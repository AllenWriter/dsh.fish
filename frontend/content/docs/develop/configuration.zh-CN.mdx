配置是插件公共契约的一部分。用明确的错误拒绝无效值，不要用静默默认值把问题盖过去。

## 定义并验证配置

导出一个 `Config` 类型和一个同名的 Schemastery schema，把默认值直接写在 schema 字段上。插件加载时，harness 会用这个 schema 校验用户配置；无效值会让加载失败，并给出可操作的错误信息。

```ts
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'

export const name = 'my-plugin'

export interface Config {
  greeting: string
  maxRetries: number
}

export const Config: Schema<Config> = Schema.object({
  greeting: Schema.string().default('Hello'),
  maxRetries: Schema.number().default(3),
})

export function apply(ctx: Context, config: Config) {
  console.log(config.greeting)  // User value or schema default.
}
```

配置里不要放秘密值：配置只携带引用，比如 `apiKeyEnv: DEEPSEEK_API_KEY`，插件在需要时通过 `ctx.credentials` 解析出真正的值。

测试缺失字段、错误类型，以及每个边界上的取值。

## 理解组合顺序

harness 在空的根配置上按以下顺序叠加出有效配置：

1. 配置档案的 `dsh.profile.bundles` 列表中每个包（bundle）的 patch，按列表顺序；
2. 配置档案自己的 `cordis.patch.yml`；
3. home 级 `$DSH_HOME/cordis.patch.yml`；
4. 每个 `--patch <path>` overlay，按命令行顺序。

后面的层按行胜出：patch 会整行替换 `config` 的值，而不是按键深度合并。当某个覆盖看起来消失时，dump 出解析后的配置：

```sh
dsh --profile demo --dump-config
```

对配置档案级和 home 级 patch 文件的修改会热重载；添加、移除或更新包则需要重启。

## 打包编译产物

只发布运行时需要的文件：编译产物、manifest、README 和许可证。测试打出来的真实 tarball，而不是工作目录：

```sh
pnpm pack
dsh plugin --profile demo add ./hello-plugin-0.1.0.tgz
```

从 Git 安装拿到的是源码而不是构建产物，所以包需要一个能在安装后构建入口文件的 `prepare` 脚本。pnpm 10 及以上版本默认拒绝运行 git 依赖的 `prepare`，用户需要先在配置档案的 `pnpm-workspace.yaml` 里显式允许：

```yaml
allowBuilds:
  dsh-hello-plugin: true
```

这个脚本在用户机器上运行，不在任何智能体沙箱之内。让它保持确定性，写清楚它的行为，并建议用户固定 commit（`github:you/hello-plugin#<sha>`）。

## 发布检查单

- 装进一个干净的测试配置档案。
- dump 并检查解析后的配置行。
- 走一遍成功、校验失败和 dispose 三条路径。
- 包变更后重启；只有 patch 编辑可以依赖热重载。
- 移除插件，确认没有留下文件、工具或后台资源。

包准备好后，选择对应的 [dsh.fish 发布格式](/docs/publish/bundle)并[提交源码](/docs/submit)。
