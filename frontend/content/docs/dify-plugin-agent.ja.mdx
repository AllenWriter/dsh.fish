## Dify の紹介

AI の知能を、水道や電力のような新しい生産資源に例えるなら、ChatGPT が火を吹いた直後、開発者は同じ車輪を何度も作っていました。API のつなぎ方、知識ベースの扱い方。Dify はその隙間で生まれ、ワークフロー編成、RAG、Agent 構築、マルチモデル管理、可観測性を一つのオープンソースにまとめました。

二年で GitHub のスターは 10 万を超え、世界のオープンソース上位五十に入りました。
![スライド 3](/docs/dify-plugin-agent/slide-03.png)
ヘビーユーザーの多くは、厳密な意味での開発者ではありません。財務、オペレーション、マーケ、営業です。ビジネス側の人がこの変化の中で黙らされてはいけません。良い Agent アプリは日常の痛みを見抜くところから来ます。Dify の仕事は、技術の敷居を下げ続けることです。
![スライド 4](/docs/dify-plugin-agent/slide-04.png)
![スライド 5](/docs/dify-plugin-agent/slide-05.png)


技術のリズムは速い。DeepSeek、Deep Research、Manus、MCP、A2A が次々と現れます。LLM API を包んで物語を語れる時代ではありません。Agent にはマルチモーダル、ネット接続、OCR、知識ベースの精度が要ります。開発者から見ると、技術が変わり、場面が変わり、時間と資源はいつも足りない。プラグイン体系は、開発をレゴのように組み合わせるためのものです。
![スライド 6](/docs/dify-plugin-agent/slide-06.png)


四つの例：

1. **Browser Use。** 日本のユーザーが貢献。ページ上の要点を拾い、たとえば連絡フォームのフィールドを見つけて URL を持ち帰ります。Marketplace で Browser と検索すれば見つかります。
![スライド 7](/docs/dify-plugin-agent/slide-07.png)

2. **Deep Research の再現。** 主フローさえ分かれば、ノードで LLM アプリを組み立て、見たままが動きます。
![スライド 8](/docs/dify-plugin-agent/slide-08.png)

3. **SSH プラグイン。** コマンドを入力し、サーバーにログインしてページをデプロイ。後半で作り方を分解します。
4. **動画生成。** API を Plugin に変える。このプラグインは私が作りました。

Dify は LLM アプリの基盤であるだけでなく、AI 能力を呼び出すオペレーティングシステムでもあってほしい。初期はツール呼び出しの入口しかなく、API 依存が強く、すでに Agent のリズムについていけませんでした。

## Dify はどうツール体系を組み直したか

### 旧体系の問題

コミュニティはよく「いつ XX モデルに対応するのか」と聞きます。多くの場合はパラメータを変えるだけなのに、再パッケージして再リリースが要りました。Dify に外部能力を足すには、API ツール一つでも、ソース一式をローカルに立てる必要がありました。
![スライド 10](/docs/dify-plugin-agent/slide-10.png)


問題をまとめると：

1. **コードの強い結合。** モデルとツールの追加が煩雑で、依存が重く、バージョン管理が難しい。
2. **ユーザー需要が閉じない。** IM をつなぐには Dify の外でもう一段 Webhook を包む必要があった。
3. **カスタムモジュールが固定。** PDF 解析や RAG を柔軟に差し替えられない。

だからツールとモデルを独立インストールできるプラグインに分け、ドキュメント解析も OCR もプラグイン化しました。Dify 内で閉じられない場面は、開放インターフェースで外部システムにつなぎます。
![スライド 11](/docs/dify-plugin-agent/slide-11.png)


エンジニアリングではすぐに次の壁に当たりました。複数 Workspace でツールが通らない、プラグイン環境の一貫性、クラウド上の数万プラグインのランタイムコスト、コードを変えるたびに再パッケージ、プラグインは Webhook を聞く HTTP サービスを常時走らせるべきか。

### 三つの鍵になる設計

**リモートデバッグ。** デバッガとランタイムを分け、ランタイム側から接続します。ローカルのプラグインが Dify と長接続を張り、インストール済みとして扱われ、デバッグモードと印が付きます。リクエストはその長接続経由で転送されます。難しいのは、長接続はステートフルなのに Dify のサービスはステートレスで、K8s の負荷分散が誤った Pod にリクエストを飛ばすこと。後にトラフィック転送で解決しました。
![スライド 12](/docs/dify-plugin-agent/slide-12.png)


**Endpoint。** Dify が IM やオフィスソフトの Webhook を受け取れるようにします。プラットフォームがランダムな URL を発行し、HTTP 転送を担う。プラグインは転送されてきたリクエストだけを処理するので、プラグインごとにサーバーを常時走らせる必要がありません。
![スライド 13](/docs/dify-plugin-agent/slide-13.png)


**逆呼び出し。** プラグインは、Dify 内部ですでに認証済みのモデル、ツール、App を呼べます。用途は、外部知識ベース（LlamaIndex の Agentic RAG など）、OCR/ASR/TTS をツールとして使う、Endpoint で OpenAI 互換 API を出す、Agent 戦略をプラグイン化すること、などです。
![スライド 14](/docs/dify-plugin-agent/slide-14.png)


### アーキテクチャの要点

SaaS は Serverless に近い弾性を採り、AWS Lambda を選びました。デバッグモードは Redis HashMap で接続状態を管理し、クラスタは IP プールを持ち、投票で到達性を測り、Master ノードが退出した Pod を掃除します。

Dify 1.0 の答えは、Chrome / VS Code / WordPress のようなオープンソースのプラグインエコシステムに頼ることです。ユーザーは公式機能を待つ必要がなく、良いプロジェクトはコミュニティに見えます。プラグイン市場は公開後すぐに 120 を超えるサービスになりました。MCP や A2A のような新しいプロトコルもプラグインとして足せます。当時の予告では、Dify は MCP をツールに接続でき、組み上げたアプリを MCP サーバーとして公開できるようになる、としました。
![スライド 15](/docs/dify-plugin-agent/slide-15.png)


## プラグインで Agent アプリをどう実装するか

Agent が目指すのは、知能的な判断に自律実行を足すことです。RPA の固定フローとは違います。いまの痛みは、安定性が低い、認知が揃わない、コンテキストが扱いにくい、検証できない、システムをまたいで手を出せない、などです。

Dify プラグインの強み：

- **開発コストを下げる。** 標準インターフェースと Schema で、モデルが呼び出し方を理解する。いつ呼ぶかはモデルに任せ、制御ロジックを減らせる。一箇所で作り、複数箇所で再利用する。
- **モジュールとして進化する。** 一つのプラグインと簡単な Prompt から始め、能力を足していく。各プラグインは単独でデバッグできる。

### SSH プラグインの書き方

ツール型プラグインから始めるのがおすすめです。構造は単純です。まずツールプロバイダを定義し、実行できるアクションを定義する。人間がサーバーにログインするときにやることは、プラグインにも対応するアクションが要ります。ホスト、ポート、パスワード、コマンド実行。
![スライド 16](/docs/dify-plugin-agent/slide-16.png)
![スライド 17](/docs/dify-plugin-agent/slide-17.png)
![スライド 18](/docs/dify-plugin-agent/slide-18.png)


手順：

1. プロジェクトを新規作成し、`manifest.yaml` を埋める。多言語も含む。
2. プロバイダ名と説明を定義する。
3. `tools/` の下に Action ごとに Python ファイルを置き、関数でパラメータを処理する。
4. `.env` にリモートデバッグのアドレス（SaaS またはコミュニティ版）を書く。Dify 一式をローカルに立てる必要はない。
5. CLI で `.difypkg` にパッケージする。apk のようなもので、分散して配れます。

インフラベンダーの多くは API ドキュメントが整っています。足りないのはすっきりした入口です。API を Dify プラグインに変えれば、生態系に入れます。
![スライド 19](/docs/dify-plugin-agent/slide-19.png)
![スライド 20](/docs/dify-plugin-agent/slide-20.png)
![スライド 21](/docs/dify-plugin-agent/slide-21.png)


### プラグインのセキュリティ

セキュリティは、極端に厳しい Sandbox ではなく署名に依ります（Sandbox を厳しくしすぎると依存がたくさん入りません）。人手レビューのあと秘密鍵で署名し、認証済みと印を付けます。未署名のプラグインは、ユーザーが設定を変えない限り、既定ではインストールできません。
![スライド 22](/docs/dify-plugin-agent/slide-22.png)


## 五つの事例

Dify には五種類のプラグインがあります。モデル、ツール、Agent 戦略、Extension、Bundle。

### 1. Dify を LLM API ゲートウェイにする

ユーザーはもともと多くのモデル Key を Dify に置いています。プラグイン化のあと、モデルプロバイダは更新がいちばん多いプラグイン種別になりました。逆呼び出しにより、Endpoint プラグインは Dify 内でホストしている任意のモデルを OpenAI 互換形式で出せます。自前モデルも同じ呼び出し方に包めます。

### 2. データベースプラグイン

数字が欲しいビジネス担当は、しばしば IT の承認待ちで、SQL が書けるとも限りません。読み取り専用のデータベースプラグインがあれば、自然言語で数字を聞けます。リスクは IT が見て、質問はビジネス側が自分でする。
![スライド 27](/docs/dify-plugin-agent/slide-27.png)
![スライド 28](/docs/dify-plugin-agent/slide-28.png)


### 3. 第三者 RAG

Dify は初期から知識ベースがありましたが、専門のベクトルストアや複雑なドキュメント解析は、別ベンダーのほうが強いことがよくあります。外部知識ベースはまず API 経由でつなぎ、プラグインができてからはよく使う外部ストアをプラグインにし、開発者ごとの重複接続を避けます。この種のプラグインは双方向通信を持ち、Cloudflare Workers に少し似ています。Query を受け、外部ストアに聞き、Dify に戻す。

### 4. 複雑な Agent 戦略

コミュニティは ReAct、Function Calling、さまざまな思考チェーンの変種を求めます。Agent 戦略タイプのプラグインなら、開発者は自分の strategy を実装し、ワークフローの Agent ノードに装着できます。
![スライド 34](/docs/dify-plugin-agent/slide-34.png)


### 5. MCP

HTTP 経由で外部 MCP サービスにつなぐ。Dify アプリを MCP サーバーとして公開することもでき、Cursor や Claude から組み上げ済みのワークフローを直接呼べます。
