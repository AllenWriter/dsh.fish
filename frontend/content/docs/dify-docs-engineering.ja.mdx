## AI 時代の知識サービス

これがやる価値があるかどうかは、AI の読み方に合わせたドキュメントをわざわざ用意する気があるかにかかっています。AI 時代の知識体系は、情報をどう組み直せばよいのでしょうか。

AI 革命が起きる以前、ソフトウェアのドキュメントはすべて人間向けに設計されていました。見た目は美しく、読みやすく。情報は層を重ねて、少しずつ深くする。SEO を脇に置いても、人間向けのドキュメントは簡潔で美しいデザインと、はっきりしたレイアウトを求めます。LLM にとって外面は表層にすぎません。必要なのは十分な長さのコンテキストです。巧みな組版ではなく、内容の厚みです。

### 時代ごとの情報検索パス

従来の検索：ぶつかった問題を入力する / プロダクト名と問題のキーワードを入力する → 検索エンジンが上位のコンテンツを選ぶ → 妥当な解決策を勧める。

ユーザー行動は三つのパスに抽象できます。

1. 検索エンジンでコンテンツを探す
2. ドキュメントの階層を辿る
3. ドキュメント内検索を使う

[Stripe のドキュメント](https://docs.stripe.com/) はこの道を極限まで押し切りました。チーム内のどの役割でも、ドキュメントの中で必要な情報にすぐ辿り着けます。ログイン済みのユーザーには、そのチーム専用のテストコードまで自動生成されます。

![Stripe ドキュメントの体験](/docs/dify-docs-engineering/stripe-docs-example.webp)

LLM と対話する時代になると、解決パスはこう変わります。LLM に尋ねる → LLM が方針を出す → ユーザーがフィードバックする → LLM が手取り足取り教える。ユーザーは各セクションを巡回したり、特定ページを検索したりせず、いまの答えを LLM に求めます。

## LLM がもたらす変化

大規模言語モデルは SEO を変えつつあり、生成エンジン最適化（GEO）を生んでいます。ある研究は、LLM からの検索トラフィックが 2024 年の全検索量の 0.25% から、2025 年末には 10% に跳ね上がると予測しました。

研究リンク：[AI SEO Study 2024](https://previsible.io/seo-strategy/ai-seo-study-2024/)

プロダクトの使い方を軸に設計された技術ドキュメントにとって、この流れは、顧客が情報を見つけ、最終的にプロダクトで成功する仕方をひっくり返します。テクニカルライターが書く内容は、LLM が対象プロダクトをどれだけ把握するかに大きく効きます。

本当に LLM フレンドリーにするには、技術ドキュメントに一つの能力が要ります。`llms.txt` の自動生成です。`llms.txt` はプレーンな Markdown ファイルで、いちばん大切な内容を簡潔に要約し、LLM が読みやすい形で構造化します。HTML や JavaScript、広告のノイズはありません。

アップグレード全体の目標はここで固まりました。

- **LLM のクロールに優しい。** GEO に全面対応し、プロダクトが AI の自然言語の答えに出やすくする。
- **API ドキュメントを持つ。** 完備して明快、オンラインデバッグとサンプル呼び出しに対応。
- **AI とドキュメントで対話できる。** 自然言語で尋ね、インターフェース説明、統合ガイド、トラブルシュートを得る。

## 動く前に構想する

### 1. 問題をはっきりさせ、GitBook を捨てる

それまでの Dify ドキュメントは GitBook を使っていました。初版のドキュメントとプロジェクトのオープンソース化を見届けたプラットフォームですが、基盤の問題が次々と表面化しました。ハイパーリンクの固着、複数人編集での白画面、極端に縦長の目次、API ドキュメントの描画異常、公開済み内容の自動書き換え、まともに動くローカルプレビューがない。

根本原因は、このプラットフォームがプログラミングをしないビジネス担当者向けで、操作の大半が GUI に依存していることです。IDE でリポジトリを引いてドキュメントをメンテすることはできますが、ローカルでは描画結果をプレビューできません。GitBook は Docs as Code のプロダクトではありません。エディタの見た目と最終公開ページもしばしば一致しません。

チームは新しい方向をはっきりさせていました。最初の決断は GitBook の使用を止め、代替を探すことです。

### 2. 目標に沿って十分に調査する

ドキュメントはプロダクトの一部です。当時 Dify のドキュメントはすでに 600 本を超え、内部の入れ子参照も多かった。新しいフレームワークの設計寿命は少なくとも三年以上であるべきです。主流の技術ドキュメントフレームワークを調査し、実測しました。比較表の全体はこちらです。[Dify ドキュメント再構築ノート](https://docs.pflm.net/zh-hans/insights/dify-docs-restructure)。

深く使ってみたあと、候補は Mintlify と Docusaurus に絞りました。

- Mintlify はビジュアルと API ドキュメントの自動生成が成熟しており、既定スタイルで大半の表示需要を満たせます。

![Mintlify 製品概要](/docs/dify-docs-engineering/mintlify-overview.webp)

- Docusaurus はオープンソースで拡張できますが、API ドキュメントの統合には追加ツールが要り、React に強いチーム向きです。

![Docusaurus 製品概要](/docs/dify-docs-engineering/docusaurus-overview.webp)

後期のメンテ、箱から出してすぐ使えること、チームの AI への投資を総合し、私は Mintlify を選びました。

![フレームワーク比較表（抜粋）](/docs/dify-docs-engineering/framework-comparison-table.webp)

## 実行

### 1. フレームワークに慣れ、小さく反復する

フレームワークが決まると、まず Demo を組み、何度も話し合い、少しずつチームの合意を得ました。Mintlify は従来の `.md` ではなく `.mdx` を使います。AI 技術がこれだけ速く動いているいま、フォーマット変換はもう障壁ではありません。構造の拡張性と、知的ツールとの融合の余地のほうが重要です。

![Mintlify MDX Demo（1）](/docs/dify-docs-engineering/mintlify-mdx-demo-1.webp)

![Mintlify MDX Demo（2）](/docs/dify-docs-engineering/mintlify-mdx-demo-2.webp)

### 2. 問題をはっきりさせ、一つずつ潰す

#### 問題 1：画像の扱いが不明瞭

旧体系には統一の画像ホストがありませんでした。リポジトリが膨らみ、命名もパスも規約がありません。GitBook はプライベートホスティングで CDN も無く、地域をまたぐ読み込みが不安定でした。

解決策：Pico + S3 で自前の画像ホストを立て、自動命名とアーカイブ。画像はメインリポジトリから切り離し、CDN で加速。過去のローカル画像はスクリプトで一括アップロードしました。

![社内画像ホスト利用ガイド](/docs/dify-docs-engineering/image-host-guide.webp)

#### 問題 2：構文が揃っていない

GitBook の hint 構文は直感的でもなく、フロントエンドの予約記号とも衝突しやすい。対比すると：

GitBook：

```md
{% hint style="info" %}
The name Dify comes from Do It For You.
{% endhint %}
```

Mintlify：

```mdx
<Info>
The name Dify comes from Do It For You.
</Info>
```

![GitBook hint と Mintlify Info の構文対比](/docs/dify-docs-engineering/hint-syntax-compare.webp)

解決策：よく使うスタイルの対応関係を Prompt に入れ、Dify Chat アプリで GitBook 構文を Mintlify MDX へ自動変換しました。

![MD から MDX への変換アシスタント](/docs/dify-docs-engineering/md-to-mdx-assistant.webp)

#### 問題 3：ハイパーリンクの参照が複雑

本番のフル URL もあれば、リポジトリの相対パスもあります。Python スクリプトですべてのリンクを拾い、置換候補をハイライトし、人手で確認してから一括置換しました。

### 3. 本番投入：移行を静かに済ませる

公開前に、ページごとにジャンプを洗い出しました。GitBook と Mintlify では URL 構造が違うので、リダイレクトは無視できません。検討の結果、A/B の段階公開はせず、核心の目標に戻りました。安定、到達可能、ユーザー体験を壊さない。公開当日はスムーズに切り替わり、大半のユーザーは気づきませんでした。API ドキュメントは DevRel の同僚の協力でその後に公開し、各ページ下部にフィードバック入口を埋め込みました。

## ドキュメントの背後にあるのは、読書体験の全体掌握

この移行は技術的な挑戦であるだけでなく、役割認識の作り直しでもありました。Mintlify はすぐにドキュメント MCP に対応しました。関連ガイド：[Dify ドキュメントで AI と対話する](https://docs.dify.ai/zh-hans/learn-more/extended-reading/dify-docs-mcp)。

![MCP 経由で Dify ドキュメントと AI が対話](/docs/dify-docs-engineering/docs-mcp-chat.webp)

Mintlify 公式の内蔵 AI 対話：

![Mintlify 内蔵 AI 対話（1）](/docs/dify-docs-engineering/mintlify-ai-chat-1.webp)

![Mintlify 内蔵 AI 対話（2）](/docs/dify-docs-engineering/mintlify-ai-chat-2.webp)

Mintlify はいまや Claude、Cursor、Perplexity など主要な AI ベンダーがドキュメントに選ぶフレームワークです。

![Mintlify を使う AI ベンダーの例](/docs/dify-docs-engineering/mintlify-ai-customers.webp)

テクニカルライターにできることは、うまく書くことだけではありません。役割はドキュメントプロダクトの責任者に近い。信頼できる内容、滞りのない読書体験、使い続けられる経路を提供することです。
