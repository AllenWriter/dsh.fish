# Deployment

dsh.fish deploys as a single Cloudflare Worker serving both the API and the
server-rendered site. See [`project/architecture.md`](../project/architecture.md)
for why the two share one origin.

## Prerequisites

- A Cloudflare account with Workers, D1 and KV enabled.
- `wrangler` authenticated (`pnpm dlx wrangler login`).
- A GitHub OAuth app, if GitHub sign-in is wanted.

## 1. Create the bindings

```sh
pnpm dlx wrangler d1 create dsh-fish-db
pnpm dlx wrangler kv namespace create KV
```

Copy the returned ids into `frontend/wrangler.jsonc`, replacing
`REPLACE_WITH_D1_DATABASE_ID` and `REPLACE_WITH_KV_NAMESPACE_ID`.

## 2. Apply migrations

Migrations are generated by Drizzle from
`backend/src/infrastructure/persistence/schema.ts` — which re-exports both the
catalog tables and the Better Auth tables, so one migration set covers both.

```sh
pnpm --filter @dsh-fish/backend run db:generate   # only after a schema change
pnpm run db:migrate:local                          # local dev database
pnpm run db:migrate:remote                         # production
```

Regenerating the auth half after changing `createAuth`:

```sh
cd backend
pnpm dlx @better-auth/cli generate \
  --config src/infrastructure/auth/auth.ts \
  --output src/infrastructure/persistence/auth-schema.ts
```

## 3. Set secrets

Secrets are never committed. `PUBLIC_BASE_URL` is a plain var in
`wrangler.jsonc`; the rest are secrets:

```sh
cd frontend
pnpm dlx wrangler secret put BETTER_AUTH_SECRET     # openssl rand -base64 32
pnpm dlx wrangler secret put GITHUB_CLIENT_ID
pnpm dlx wrangler secret put GITHUB_CLIENT_SECRET
pnpm dlx wrangler secret put GITHUB_TOKEN           # crawler, read-only
pnpm dlx wrangler secret put ADMIN_EMAILS
```

`PUBLIC_BASE_URL` must be the real origin. It is read by `readConfig`, which
throws when it is empty rather than defaulting — a wrong origin silently breaks
OAuth callbacks and cookie scoping, which is far harder to diagnose later.

The GitHub OAuth app's callback URL is
`<PUBLIC_BASE_URL>/api/auth/callback/github`.

## 4. Deploy

```sh
pnpm run deploy
```

This builds the client assets and the SSR bundle, then runs `wrangler deploy`.

## Scheduled ingestion

`wrangler.jsonc` registers a Cron Trigger (`0 */6 * * *`). Each firing runs the
`IngestCatalog` use case, which sweeps the GitHub `dsh-plugin` topic and npm and
folds the results into the catalog. It is deliberately tolerant: one malformed
package upstream must not abort a sweep.

Trigger a sweep manually as an administrator:

```sh
curl -X POST https://dsh.fish/api/v1/admin/ingest \
  -H 'content-type: application/json' \
  -H 'cookie: <your session cookie>' \
  -d '{"limitPerSource": 50}'
```

## Local development

```sh
pnpm install
pnpm run db:migrate:local
pnpm run dev
```

The Vite plugin runs dev and preview inside workerd, so local behavior matches
production bindings rather than a Node emulation of them. Local values come from
`.dev.vars` (copy `.env.example`).

## Operational notes

- **Per-request container.** D1 and KV bindings arrive per request, so
  `createContainer` runs per request. It is cheap: no pools, no warm-up.
- **KV minimum TTL is 60s**, which is why the Better Auth rate-limit window is
  60 and cannot be shorter.
- **D1 has no cross-statement transactions.** Multi-table writes go through
  `db.batch`, which D1 applies atomically; large crawls are chunked to stay
  within the batch cap.
